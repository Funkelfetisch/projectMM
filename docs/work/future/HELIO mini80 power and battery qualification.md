# HELIO mini80 power and battery qualification

The owner maps the wearable mini-HELIO to the current 8 cm PCB and Fusion design. The [source profile](../../reference/helio-mini80-profile.json) records the current S3-N8/52-pixel design and its source hashes. The older C3/16-pixel concept is not this product. The pre-S3 power-sequence document names GPIO10/7; the v289 PCB MCU pads21/27 and S3 pin map instead bind enable GPIO17 and data GPIO47.

Implement a fail-closed power lifecycle before offering an installable mini profile: preload enable and DIN LOW before output setup, keep DIN LOW while enabling VLED, wait a board-qualified maximum settling interval, transmit and latch a 52-pixel black RGBW frame, then start visible output. On off/sleep/reset, stop and drain output, latch black if supply is valid, hold DIN LOW, disable VLED, and retain the low state. Restart repeats the entire sequence. The generic relay feature does not establish rail settling or black-before-visible ordering.

The cold-initialization owner can now shut down before any RMT pin or frame is
configured: after both GPIOs were successfully preloaded low, this narrow case
still performs a checked peripheral detach and reasserts both lows. The regular
resolved-pin check remains mandatory after a driver is configured or attached.
The rebuilt desktop mini-power selection passes 23 cases / 656 assertions,
including immediate shutdown and existing wrong-pin and failed-detach cases.
This is software evidence only; the adapter is not a selectable product and
no electrical behavior or rail-settle time has been measured.

The current integration points require a stronger completion signal. `Drivers::applyRelay` changes the power GPIO immediately when master power or brightness changes; it does not sequence DIN, settling or a black frame. `RmtLedDriver::tick` starts transfers from the current effect buffer, and `waitForPins` reports completion only for transfers whose start returned true. A false transmit result therefore cannot be treated as a successfully latched black frame. A mini-specific lifecycle must gate visible transfers, retain the black buffer until every started transfer completes and the reset-low interval has elapsed, and report failure if a transfer cannot start or finish. On shutdown it must similarly prevent new visible writes before draining. Exercise failed start, timeout, repeated on/off and a configuration change during each phase on the host; qualify the rail delay and waveform on the actual board before enabling the profile. These are source-level requirements, not evidence that the mini board has been tested.

The working tree now records RMT frame completion only when all used transmit starts succeed, their waits complete and the configured reset interval elapses. A timeout retains the frame; a failed start prevents confirmation. The driver can also hold normal output, send a zero-valued frame and release that hold only after software completion; retry after a failed start is explicit. The black-frame status distinguishes idle, pending, completed and failed attempts for a future power sequencer. Host tests cover a failed individual pin, a delayed completion and a black request during an existing transfer. This software signal does not read the physical DIN waveform and is not yet connected to a mini-specific power lifecycle; board timing and physical latch still need qualification.

The existing ESP32 `gpioWrite` configures output mode before setting its requested level. It therefore does not establish the required preload-before-enable ordering for the mini's DIN and VLED enable. The working tree now provides a separate checked `gpioPreloadLowOutput` operation that programs the output latch low before configuring output; it rejects invalid and reserved ESP32 pins. The caller must first detach any peripheral, and the mini path still needs a qualified GPIO-to-RMT ownership handover. An unavailable driver or source buffer keeps black-frame status pending and visible output held in the host test. Neither that test nor the ordering of SDK calls proves the physical pin level or the ownership handover.

The source now contains an unbound `MiniLedPowerSequence` policy with explicit nonzero settling and black-frame timeout values. Its adapter must hold visible output, detach and hold DIN low, preload and switch the rail, attach RMT and translate the driver's black-frame status. Host tests run the policy against the desktop RMT driver and a simulated rail, including 52 four-channel zero output, cancellation, clock wrap, failed transfer, timeout and failed handover. A failed handover cannot be reported as safe-off. The real adapter, validated board timing and electrical measurements remain prerequisites; no product instantiates the policy yet.

The working tree also provides `rmtWs2812DetachChecked`: it refuses an unfinished transfer and retains the handle if channel disable, channel deletion or encoder deletion fails. An ESP32 retry remembers a channel already disabled. The shared phase policy is exercised with simulated failures at each SDK operation, including retries after a partial detach; the S3 implementation compiles against the pinned SDK. The mini adapter must use this checked path rather than the legacy best-effort deinit. Tests do not inject failures into the actual SDK; GPIO-matrix handover and physical DIN measurements are still required.

`RmtLedDriver::detachForPower` and `attachForPower` now use the checked path while holding visible frames. A failed detach blocks reinitialization and retains the frame buffer for retry; attaching requests a fresh black frame before visible output can resume. Host integration tests connect these methods to the mini policy with a simulated rail and GPIO handover, including a refused detach that leaves safe-off unacknowledged. Calls must be serialized with the driver's tick, and the board adapter must own the driver for its entire active lifetime, not only while the black hold is active. These methods do not themselves switch a GPIO or prove a physical level. The actual board adapter and profile remain unbound.

A power owner can require an exact light count and output channel count when requesting black. A short source window or wrong channel count then fails the black-frame gate without transmitting, and these requirements survive detach and reattach. The mini adapter must request 52 lights and four channels, verify the single physical data pin separately, and repeat those checks throughout its exclusive ownership. This host-tested gate does not qualify the mini's colour order, timing or actual electrical output.

The unbound `Mini80PowerPort` connects that policy to checked RMT detach and the platform GPIO calls for data GPIO47 and enable GPIO17. It checks the resolved one-pin, 52-light, four-channel output before switching on, attaching and releasing visible output. Desktop integration tests exercise a full on/off sequence and reject a different output pin. The adapter is not instantiated by a product: a safe early-boot ownership integration, serialized configuration access, board-qualified settling interval and physical signal and rail measurements are still required. The host GPIO states are simulations, not measurements.

The adapter also rejects direct out-of-order rail or attach calls and compares the current pin and window controls with the resolved wiring before enabling. A host test changes the data-pin text during settling: the start fails, the original resolved output is detached, and simulated DIN and rail are held low. This check does not replace exclusive ownership or make concurrent control changes safe.

After a successful checked shutdown, `Mini80PowerController` now drops its
initialized state so a late tick cannot re-enable the rail. Restart requires a
new cold preflight; an unsuccessful shutdown keeps the controller initialized
so the checked handover can still be retried. The 23 mini host cases pass 660
assertions, including a late tick after shutdown and a fresh preflight. This
does not resolve module ownership during failed teardown or qualify real GPIO.
An additional desktop integration test injects a checked RMT detach failure
while the mini sequence is on: shutdown reports failure, a new cold preflight
is refused while ownership is retained, and a later successful shutdown leaves
the rail off even after a late tick. This verifies the standalone controller's
retry contract only; the module tree still cannot retain it after failed
release and must not yet expose the mini driver.

**Lifecycle integration is still a blocker, not just a registration task.** The current `MoonModule::release()` returns no result. `StateDocument` removes or replaces a child, calls `release()` and deletes the old tree regardless of whether an RMT detach or rail-off command succeeded; `Scheduler::release()` similarly deletes all trees after release. Disabling a module or an ancestor also reaches `release()` through `applyState()`. Consequently, simply calling `Mini80PowerController::shutdown()` in a new driver's `release()` would discard its owner and buffers even when shutdown returns false, contrary to the checked-detach contract. A future integration must keep the controller, driver and transfer buffer alive and prevent reuse of GPIO17/47 until a checked shutdown succeeds, including disable, removal, replacement, ancestor teardown and scheduler shutdown. It must also serialize pin-setting and relay mutations with that ownership; the cold preflight alone is only a snapshot. The failure and retry paths need integration tests through the real lifecycle, not only tests of the standalone sequence. Do not register the mini profile until this ownership and the board-qualified timing are resolved.

If the source buffer disappears after startup, the adapter can still detach the resolved data pin and command rail-off without falsely claiming a completed black frame. A host test exercises that fault path. An ESP32-S3 compiler syntax check also covers the unbound adapter against both existing HELIO and NEBULITE build configurations; it does not link or run an enabled mini product.

Qualify the actual emitter order/timing, switched-rail startup/discharge, native W and mixed RGB, battery/USB transitions, charging inhibit, low-cell cutoff and current, deep sleep/wake, ambient sensor and microphone. The PCB's limiter fault pin is not an observed firmware input. Do not infer current or remaining battery from an uncalibrated voltage alone. Keep continuous light independent of Wi-Fi inactivity; BLE remains available without network setup. Use the actual cell and power-path limits, not a runtime promise from its nominal capacity.

Design and mechanical CAD establish identities and intent. Prototype measurements establish waveform, optics, battery, thermal and RF acceptance. The small board is not enabled through the existing sphere's GPIO35 profile, and its colour order and rail-delay fields remain unqualified until tested.

The standalone mini controller now clears the RMT handover guard after a confirmed software detach and rail-off command, before releasing its ownership and pin reservations. A wrong owner, an attached output or a failed detach cannot clear the guard. The controller exposes a nonblocking shutdown step for a future owner: it requests and latches black during normal shutdown, then commands DIN and rail low, and releases resources only after checked handover. On a fault it attempts safe-off and retains ownership if that fails. A desktop test-only owner integrates this with the real scheduler: simulated RMT detach failure keeps the module tree and both pin reservations, and a later successful retry releases them. The production mini owner is still unimplemented and unregistered; physical black transmission, GPIO, rail timing and battery behavior remain unverified.

Battery sampling has a separate ownership gap: its worker checks conflicts between its configured channels, but does not reserve its ADC and switched-divider GPIOs in the scheduler. The previous stop path requested inactive gate levels while discarding failure returns. A late worker is serialized by `BatteryGateGuard`, yet that does not prove the physical switch is off or keep another module from acquiring the pin after a failed GPIO call. Before enabling a switched divider on a product, implement a serialized pin claim and a retryable, reported gate-off handover that retains ownership on failure; test configuration changes, removal and teardown as well as sampling. The unbound MINI80 LED-owner shutdown test does not cover this battery worker.

The stop path now checks the inactive-gate GPIO result and retains the stopped worker context on failure, reports an error, blocks a replacement sampling worker and retries the gate-off command. A failure while sampling also stops the batch and discards that sample. The battery/BAS desktop filter passes 52 cases / 742 assertions, including injected gate-off failures and successful retries. This is a partial software safeguard: the sampler does not yet reserve its pins, and tree removal can be validated before a concurrent gate failure is known. It does not establish a safe physical handover or support activating the unqualified MINI80 divider. The default configuration does not enable a gate, but the general battery controls can explicitly configure one; they are not globally disabled.

After a gate-off failure originating in sampling, the service requests a new preparation rather than joining a worker from the render tick.
