# Legacy ESP32 updater: bytecode evidence

The recovered production APK `recovered-apks/io.nebulite.esp32updater.apk` in the NEBULITE app worktree has SHA-256 `55101f4df706d94463e5230e2dc2d961826ebe4512d4b5b5f7a4d73580fd79bd`. Its embedded `assets/index.android.bundle` is Hermes bytecode version 96. A local, non-executing disassembly with `hermes-dec` 0.1.4 was written to `/tmp/nebulite-legacy-updater-inspect/disassembly.txt`. Function identifiers below refer to that bundle. This is static analysis, not a device test or proof that a new controller implements the protocol.

- Function 9237 constructs `http://update.nebulite.io/nebulite_esp32_` + its argument + `/firmware.bin`, downloads to the app document directory, checks for HTTP 200, and reads the file as base64. The old server URL is plain HTTP. The exact argument selection has not yet been independently traced.
- Function 9256 requests MTU 255 and sets the packet size to the returned MTU minus 3; the initialized fallback is 20 bytes. It looks for UART service `6E400001-B5A3-F393-E0A9-E50E24DCCA9E` and RX characteristic `6E400002-B5A3-F393-E0A9-E50E24DCCA9E`, writes `{"g":false}\n` without response when found, waits 3000 ms, and reconnects. For OTA it selects the first service UUID containing `180a` and characteristic UUID containing `b00c`; these are substring matches, not verified full UUIDs.
- Functions 9256, 9262 and 9264 split the downloaded bytes into MTU-sized chunks, append an empty chunk if the final chunk is exactly full-sized, subscribe to notifications on the selected characteristic, and write the first chunk without response. Every notification callback without an error invokes the next write; the callback does not inspect notification payload. This does not establish what the device acknowledged or whether it persisted data. The generated base64 is the BLE library input encoding, not evidence that base64 text is sent over radio.
- Function 9264 treats a notification error as success when the next-chunk index is at least the chunk count minus two; otherwise it displays an error. This comparison applies to the callback error generally, although the message describes a disconnect. This UI interpretation does not verify a committed image or rebooted firmware. The early failure message asks the user to press the controller reset button.
- The user interface calls itself `NEBULITE Uralt Firmware Updater` and displays download/upload progress. This is distinct from the earlier Funkelapp Nordic DFU ZIP flow, and from MoonLight's update mechanism. Do not infer cross-compatibility, authenticity verification, recovery or production safety from this disassembly.

The APK was read only, no binary was installed and no device contacted. The bundle and generated disassembly under `/tmp` are working copies; the source APK remains unchanged.

## Retained web updater source

The original `nebulite-updater/data/index.html` was read from the independently restored local archive at `/home/veit/.local/share/auravia-ovh/config/hetzner-retirement-20261006/offsite-restore/home/veit/.local/share/auravia-ovh/restore/cax21-unmounted-20260909/unmounted.tar`. Its SHA-256 `ce9302863ba3bc7ad2454d7847bc33951e55ef08f16ac767d91f615d39272e83` and size match the retained inventory. This corrects the earlier incomplete inference that the web updater only offered USB.

- The page selects Controller A (identified by its code comment as ESP32-S3), or Controller B (identified as ESP32). For B, it asks whether WLED and Wi-Fi are available; otherwise it links the separate Android updater APK and iOS TestFlight. This shows the page and app were part of the same update journey, not that either was generated from the other or that the linked APK is byte-identical to the recovered APK.
- The web page offers USB through `esp-web-install-button` and a product-specific manifest, and Wi-Fi through a downloaded `combined.zip`. The Wi-Fi code extracts `firmware.bin`, sends a raw HTTP POST to `http://4.3.2.1/update`, then uploads files from `files.zip` via `/upload`, with `cfg.json` last. It offers backups of `cfg.json` and `presets.json`; the ZIP upload can replace configuration. Wi-Fi redirects to the old HTTP-only hostname; USB expects HTTPS.
- The archived five USB manifests all declare `ESP32-S3`, including the two `nebulite_esp32_*` paths selected by the older-controller branch. This discrepancy makes actual classic ESP32 USB compatibility unproven. The code does not establish successful HTTP updates either: transport behavior, endpoint compatibility, image suitability, reconnect and recovery all require independent verification. The original `fetch(..., {mode: "no-cors"})` reachability check does not verify installed firmware identity.
- The page itself does not implement a Web Bluetooth transfer; its older-controller app link is separate. All analysis is static and read-only. The archive remains inactive; no device was contacted or flashed.
- On 2026-10-29 the original Expo APK link returned HTTP 400 with `BUILD_NOT_FOUND` and `The requested artifact is not available.` No APK bytes were obtained, so it cannot be compared with the recovered Honor installation. The latter's recovery record identifies it as the `nebulite-updater` project, version 1.0.0, but does not prove that it was the exact build linked on the page.
- The retained per-file SHA-256 inventory was also checked against each product's archived `firmware.bin` and `merged-firmware.bin`. The app image header's little-endian chip ID at byte 12 is 0 for both `nebulite_esp32_*` products and 9 for both `nebulite_esp32s3_*` products and HELIO 1. Each of the four garment app images is present byte-for-byte at offset `0x10000` in its merged image. Thus the archive does include distinct classic ESP32 and S3 app images; the classic product USB manifests nevertheless declare ESP32-S3. These header checks do not qualify the combined images, partition layout, USB installer behavior or the firmware on any physical controller.
- Veit clarified that the classic ESP32 controller had no onboard USB: serial flashing required an external USB-to-serial adapter. Native USB on the ESP32-S3 is a different hardware route. In neither case does a manifest alone establish the wiring, boot-mode entry, partition compatibility or a working update.
- The archived classic product packages contain `files.zip/cfg.json`. Their outer `combined.zip` SHA-256 values match the retained `archive-inventory.json`: crop-top `3eb8a8e04d8efb34ba0fd4a96f35bb9e54c47831c39de8716c0dc4b12680fbd1`, jacket `e8cdc01b73917e0a2bbc6f4d0167877917f3b73ba7e00b11849080e18162b3ff`. The crop-top configuration (SHA-256 `0db5ae2cecd0754d18c4fd8bdba411c4e80c17100bb3e55edf3ec13d1d6b22ae`) declares one WLED LED bus on GPIO26, start 0, length 8, type 22 and order 1; it declares no separate white output. The classic jacket configuration is `{}` (SHA-256 `44136fa355b3678a1146ad16f7e8649e94fb4fc21fe77e8310c060f61caaff8a`) and does not establish its pinout. These are archived updater settings, not evidence that any particular garment has that wiring, that its battery or charging signals are known, or that a MoonLight setup can safely be applied. No product profile or pin was activated from this evidence.
