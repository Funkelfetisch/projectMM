# Connectionless lighting control

Veit clarified that connectionless control was an idea, not a requirement: the priority is responsive controls and no disruptive connection-slot limit. Keep the existing connected protocol while measuring the delay and improving the proven path; retain this broadcast investigation as an optional future direction. A packet specification, radio integration and phone validation remain open. Existing RPC2 and standard Battery Service remain available.

## Historical source

The original [NEBULITE Smart Bluetooth source](https://github.com/Funkelfetisch/NEBULITE-Smart/blob/ca321b4ca4682718974a956def42d4f958691bc6/src/bluetooth.cpp) implements controller-to-controller group mode for nRF52, not the ESP32 implementation: `include/bluetooth.hpp` marks ESP32 as TODO. It scans advertisements, tracks peers and elects a master; a follower applies its master's pattern and variables. The old phone interface is separately connection-oriented BLE UART. Thus this source demonstrates the intended controller broadcast idea, not a complete stateless bidirectional phone protocol.

The master advertises a 25-byte AD structure: length 24, type `FF`, bytes `0B B0` (the author's BOOB marker, interpreted as little-endian `0xB00B`), role 0, 32-bit uptime in native byte order, 16-bit follower count little-endian, three pattern-ID bytes and 11 variable bytes. Follower packets use role 1, six master-address bytes and three pattern-ID bytes. Scanning is configured at 100 ms interval and 50 ms window, with an RSSI threshold of -80 dBm; advertising is configured at 20 ms. These are source settings, not measured latency, coverage or compatibility.

Do not port the old implementation unchanged: it keeps master/peer state, its broadcast function carries an explicit crash warning, and `previousSlaveData` has 23 bytes although the comparison and copy use 25. The manufacturer-specific field requires an assigned company identifier; a private marker alone is not proof of ownership of that identifier. An interoperable identifier and framing must be selected for the new protocol.

## Design and acceptance

- Specify compact versioned absolute-state commands, individual and group addressing, source identity, stale/duplicate handling, and status advertisements. Repetition and observed acknowledgement must not be represented as guaranteed immediate delivery. Avoid unbounded queues, relaying loops or implicit association with unrelated nearby lamps.
- Determine actual Android advertising and scan support on the target phones, foreground and background behavior, the response/update latency and coexistence with Wi-Fi and rendering. Confirm whether and how iOS can transmit the chosen frame using supported public APIs before claiming cross-platform support.
- Reconcile the exact wire format with the app owner before implementing an incompatible mobile client. Test multiple lamps, multiple phones, packet loss, reordering, reboot and nearby groups, and preserve the current working app until the replacement meets those tests. Native Android battery display and firmware updates need separate standard-compatible solutions; a custom broadcast alone does not establish either.
- A live candidate requires a safe recoverable build and explicit device-window coordination. Neither source archaeology nor host codec tests establish physical group synchronization or radio reliability.

The existing connection-based candidate's eight-peer transport table is separately covered by three focused host cases and 116 assertions, including eight pending requests, isolated replies, disconnect and stale-result rejection. This does not implement or qualify broadcast.

## Current S3 transport constraints

The present firmware explicitly disables NimBLE observer mode, so it cannot currently receive broadcasts. Its single legacy advertising set is already used for RPC discovery and its 31-byte scan response is fully occupied by the 128-bit service UUID and 13-byte product hint. With eight connected clients, advertising and scanning also require ten controller activities, while the current eight-client candidate configures nine. Supporting broadcast therefore needs observer lifecycle, an activity-budget change and a compatible advertising strategy; simply adding a handler would not work. Concurrent radio roles and the existing host start/stop ownership must be qualified before a device flash. ESP32 classic has a different controller configuration and must be assessed separately.

These two operations do not measure optical response, current app behavior or the reported five-second experience. The current app source polls the state characteristic until the correlated response, with a 25 ms delay only after a nonmatching read; the timeout is six seconds, not an intentional six-second wait. Group connections first attempt retained parallel links, then try retained sequential establishment and only fall back to connect-per-command when concurrent links cannot be retained.
