# Product setup

The NEBULITE dashboard offers product setup directly in its Setup section. Choices come from the same [device-model catalogue](../../mooninstaller/deviceModels.json) as the installer, filtered by the running firmware and reported chip family. A new unconfigured output opens the section; existing custom output wiring keeps it collapsed.

The shared codebase currently has separate HELIO and NEBULITE firmware targets. This menu selects a compatible output profile; it does not switch firmware families or read PCB hardware-ID inputs. Automatic board identification is not implemented.

Applying a choice sends one native state document containing only `System.deviceModel`, `Drivers` and `Layouts`. Output and layout children follow the selected profile and are explicitly enabled. The parent groups' enabled state is preserved. Radio, battery, audio, effects, groups and preset configuration are outside this operation. The dashboard confirms the actual model, enabled outputs, output settings and layout before reporting success; a model name alone is insufficient. An uncertain write response exposes a readback action rather than automatically replaying the write. The general state API has no atomic configuration precondition for concurrent setup clients.

The phone applies the same choices over BLE with the `setup` operation ([product BLE](product-ble.md#product-setup)), since a NEBULITE firmware boots with Wi-Fi off. The generated browser table and its firmware twin `src/helio/ProductProfiles.h` are checked against the catalogue when bundling. Regenerate both with `uv run moondeck/build/gen_product_profiles.py` after changing these product entries.

The four 2021 ESP32 products follow the NEBULITE Smart ESP32 v0.5.0 source (`Funkelfetisch/NEBULITE-Smart` 9fbc10e1, `src/neopixel.cpp`): Croptop 8 and Fanny pack 4 RGB pixels on GPIO26, Backpack 6 on GPIO26 mirrored on GPIO17 and laid out as two columns down and back up, Jacket 50 split 19, 19 and 12 over GPIO26, GPIO17 and GPIO18. Each awaits physical qualification on its controller.

The HELIO necklace is the 8 cm dome worn on a neck string, a `nebulite-s3` setup choice for the MINI80 SIDE43 board (`helio-pcb` `variants/helio-mini-80-side-43`). Its numbers come from that board's native file, `audit-work/mini80-side-led-20261102/after-variable-USB-pair.json` (source SHA256 70036c56…, strict DRC 0): 43 SK6805SIDE LEDs in one ring, faces at a 37 mm radius pointing inward, LED1 at 4.186° from the USB edge and one every 360/43° counter-clockwise seen from the dome, LED k's DOUT feeding LED k+1. Module pad 27 (GPIO47) drives LED1 through a level shifter that isolates the line while the rail is off, and pad 21 (GPIO17) enables the LED rail, so the profile lists GPIO17 as the Drivers relay. The SK6805SIDE datasheet sends green, red, blue, white and its timing fits the default 800 kHz preset. The layout is a point map on a 15 by 15 field, radius 7, the RingLayout spacing for 43 lights, with the board's +y edge up; the housing that carries the string loops is not modelled yet, so which edge hangs up is an assumption. Microphone and ambient light sensor keep the MINI80 pins. Battery, the qualified LED power sequence and light output await the board.

Before any module starts, both NEBULITE firmwares settle their board pins. `nebulite-esp32` drives the buzzer's GPIO5 low and pulls GPIO2 down; `nebulite-s3` drives the Rev4 battery controller's enables, GPIO21 and GPIO14, high when GPIO10 reads high, and holds them with the ESP32-S3's pad hold, so an update's restart, a reboot or a crash keeps the controller on. The reset button pulls EN low, which switches the chip off and its pads with it, so it still turns the controller off. Each prints the pins as their pads read back, level, output driver and internal pulls, on the serial console: `Board pins: GPIO5 LOW out GPIO2 LOW pull-down` on the classic board. Both boot with Wi-Fi off, so the phone app over BLE is the way in. An unnamed controller is `NEBULITE-` and its MAC's last four hex digits, its network name and the name it advertises.

## Source profiles and manual white

The available Croptop and Jacket S3 entries remain source-verified prototypes, with physical controller acceptance pending. The owner confirms that jacket and vest use the same product profile; setup displays both names while retaining the existing Jacket S3 identity. Their extra logical element is a separate single-channel PWM output, not an additional RGB pixel.

The historical release's WLED `const.h` names order 1 RGB, type 22 WS2812 RGB and type 41 single-channel PWM. The archived release configuration uses those values for both product outputs, and the MoonLight profiles match the order, logical ranges and pin numbers. WLED's configured gamma and power handling are separate from this mapping; matching the wiring does not establish identical brightness or colours.

The pinned WLED source is `AuraviaLTD/WLED` commit `8c58252cc2f1c0edb1d52b39a625052ed86b8a8c`, `wled00/bus_manager.cpp`, blob `231a23859f5c55fd027088f777ad2d16339c7b15`. Type41 writes the W channel after the configured white calculation and scales it by master brightness before PWM output. Both stored product configurations select manual white. Their MoonLight PWM profiles therefore use `whiteMode: None`; RGB animation does not implicitly become a new maximum-channel white rule.

An enabled output carrying a native white channel requests four source channels through the shared fixture layout. RGB-only rigs retain three; existing wider layers are preserved. Fine-channel output uses the same separately resolved cold and warm white values as the byte and wide-PWM paths.

Historical colour gamma is 2.8 with brightness gamma disabled. The current profile curves remain explicit port choices or existing defaults; exact historical optical equivalence is unqualified. Battery divider values, presence, calibration and charging require a separately selected and qualified board revision. Product selection does not activate the old unverified battery calibration.

The battery sampler rejects a switched divider gate that overlaps either declared battery ADC input, including a channel whose divider configuration is incomplete. Changing or disabling a channel stops its in-flight sampler; a subsequent prepare applies the new configuration. With a live scheduler, it checks declared pin controls, pin lists and fixed pins, and reserves the selected ADC and gate pins while sampling. These cooperative reservations do not detect undocumented or noncooperating users of a pin and do not establish electrical safety or the wiring of a particular board.

Scene cards use a labelled linear RGB strip simulation with the selected layout's light count. They do not claim the garment's physical LED geometry. When live setup readback matches a source profile, the independent white PWM slot is excluded from the displayed RGB strip while logical sample positions remain unchanged. White is not mixed into RGB pixels. The independent white output and physical appearance require a product-specific preview and device validation.

The dashboard hides cached battery values when its controller connection closes, and shows them again only after a fresh state response. This does not establish battery presence, calibration or physical charge accuracy.

When the live S3 crop-top setup matches its known RGB and white outputs, scene cards can use the recovered eight-pixel WLED garment illustration. Its historic geometry is approximate, and the separate white output is not depicted. The matching S3 jacket/vest profile instead shows its three 30-pixel RGB outputs as a labelled schematic, sampling their actual logical positions around the independent white slot. This diagram does not represent garment geometry; the older 50-pixel jacket geometry is not applied to the 90-pixel S3 jacket. Unconfirmed wiring uses the generic strip preview.

The product home also shows a live source preview for those matching profiles when the preview stream supplies a complete, ordered one-dimensional frame. The crop-top uses the historical illustration and the jacket/vest uses the RGB output diagram. These are pre-driver RGB source values, not corrected or measured LED output; the separate white output is not shown. Missing, stale, coarsened or mismatched frames leave the product illustration visible instead of reusing an old preview.

Historical segment bounds are logical output positions, not a count of RGB pixels. The archived Snowflakes segment `[0,9)` covers eight RGB positions and the separate white position on the source-derived S3 crop-top profile. The jacket segment `[0,31)` covers the first 30 RGB positions and the white position; the other RGB outputs begin at 31 and 61. This is a source-level mapping for review, not proof that a particular physical board or garment is wired that way.

When the streamed state omits select metadata, setup reads the Drivers metadata before identifying existing wiring. The UI shows a checking or unknown state until then and preserves a deliberate product selection during the read.

The provisional Snowflakes port follows the current MoonLight master brightness when choosing the original WLED low-brightness fade branch. With `follow master` disabled, `source brightness` supplies a manual reference instead. The archived preset was stored at full master brightness and its review candidate retains 255 as that reference. The control changes fade behavior; actual output brightness is still controlled by the master and driver correction. Actual WLED/device equivalence remains unverified.

Setup also offers approximate 2D animation layouts. The crop-top map places eight RGB output positions using approximate anchors from the archived illustration and retains the separate PWM white slot. For the jacket/vest, Veit describes 30 physical RGB LEDs in the order bottom, top, hood and two sleeves. Its candidate places those 30 points plus the PWM slot on a 2D field and uses the first archived 30-slot RGB output. The archived configuration lists three such outputs; its configured slot count is not evidence of 90 physical LEDs. The candidate pin and actual wiring remain unverified. An optional parallel Y branch can cause two positions to share a signal and cannot be assumed independently controllable.

These are editable approximations, not measured garment maps. The preview reads the actual edited output-to-field map, while the garment artwork keeps its own physical output order. Applying a layout explicitly changes setup and verifies the selected output and map; existing settings are not changed automatically. Scene cards sample the 2D field at each output position and feed those strip values into the existing garment simulation. The live simulation requires a complete coordinate table in output order. The independent PWM white slot is not displayed as RGB. The original one-dimensional source configuration remains available. The 30-LED jacket preview uses the historical illustration and the selected output order as an approximate, front-view animation; it does not claim measured optics or physical wiring.
