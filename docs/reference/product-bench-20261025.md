## BLE and network transition

Linux BlueZ and an Android 13 tablet both paired, bonded and accessed the encrypted lighting service. Fragmented commands, execution readback, on/off, brightness, RGBW, catalog and single-device scheduled/group commands were exercised. Linux bonding survived application OTA/restart. The tablet's nearby RSSI was approximately −56 to −62 dBm, versus around −81 dBm through the wall from the Linux host. Radio weakness does not explain a CPU panic.

A reproducible Wi-Fi-return panic was captured in retained RTC metadata and decoded with the exact immutable ELF. The stack enters `esp_netif_is_netif_up` from mDNS `join_group` / interface initialization. Stopping advertisements left the mDNS worker and cached network-interface references alive while Wi-Fi destroyed its interfaces. The fix calls `mdnsShutdown()` before stopping station or AP, then permits a fresh initialization. A host regression verifies this order. On image SHA256 `c45baa5f5c3665c613e96e4ef37f7fd1843bc81b14116a9902f31f2dc43e495c`, three tablet-mediated Wi-Fi-off/on cycles, including keeping BLE connected after LAN return and disconnecting later, passed with continuous uptime and unchanged retained panic sequence. The old record is deliberately retained; its presence alone does not mean the new image panicked.

The same bench exposed a separate resource problem: persistent BLE left roughly 40 KiB internal heap at idle, below MoonLight's 50 KiB HTTP send admission floor. API replies arrived but embedded assets stalled after their headers. Product-only NimBLE/Wi-Fi queue sizing recovered about 21 KiB. WebSocket/page-load allocations could still push free RAM below the generic floor, so these products now use the existing 32 KiB allocator reserve with 1 KiB send chunks; generic builds retain their defaults. Both embedded-file and fragmented-state regressions pass. On image `01cb6c49dfe2b0c1f18b7d28e5ffa2a6ac050f544cb7ac2c07976a9281abba63`, actual Chromium checks at 1280 and 390 pixels loaded the custom dashboard, displayed its live preview and brightness controls, found no JavaScript errors or horizontal overflow, and opened MoonLight at `/modules`.

## Persisted offline boot and USB recovery

Saving `wifiEnabled:false` and restarting exposed an independent startup panic. The Windows CP210x UART trace captured `xQueueSemaphoreTake` asserting on an uninitialized queue. Decoding against the exact ELF reaches `sys_mutex_lock`, `tcpip_send_msg_wait_sem`, `netconn_new`, `lwip_socket`, `TcpServer::open`, HTTP setup and scheduler setup. Socket setup preceded radio initialization, so a boot without Wi-Fi entered lwIP before its TCP/IP core existed. The correction initializes the shared network core before opening UDP sockets or the HTTP TCP listener, independently of radio association.

The owner completed USB recovery to HELIO application SHA256 `9a0040ca4526aa4ad6d2923f4411114a0faddec9aca2ff625bb327c0b9c1d123`. The recovery log verifies the expected MAC and both application-slot writes. It preserved NVS, bootloader, OTA metadata and LittleFS. The corrected application boots with Wi-Fi disabled and continues rendering, but its initial BLE connection attempts failed from both Linux and the nearby tablet. This earlier image did not earn offline-control acceptance. The upstream Improv serial state operation successfully restored `Network.wifiEnabled:true`; LAN access is restored. A live RFC2217 UART relay through the owner's laptop permits subsequent diagnosis without repeated manual downloads. The separate NEBULITE candidate compiles but has no physical acceptance.

## Animation freeze regression

On the recovered application, effect execution and the RMT driver continued while 39 preview frames over four seconds were identical. Temporarily disabling multicore output restored changing frames: 41 unique frames in 49 samples. The ported task-diagnostics barrier incorrectly invoked the structural render-worker teardown every second. After teardown, the retained output buffer for one identity-mapped layer was no longer refreshed.

The correction gives read-only task snapshots a completed-frame barrier that preserves the worker. Composition also updates every allocated output buffer after a worker fallback or structural quiesce. A regression reproduces the stale buffer before the correction. All 2,825 C++ cases and 183,029 assertions pass after it, including repeated snapshots with changing frames. Native HELIO application SHA256 `42d336b258aebc5d2beaec5cfc5847123b230ca012693f09425c391eee7a89e7`, matching ELF SHA256 `18eae3d553d93a55ef16f262adbddc8251e0c1b398a62325ee411f9ac6b3eb5c`, identifies the earlier recovered reference image. Its HTTP upload aborted. The first USB attempt lost the laptop's LAN connection mid-write; the complete retry over its Tailscale address verified both application slots. The boot UART independently identifies the matching ELF. Bootloader, NVS and filesystem were preserved.

With multicore restored, 193 different preview frames were captured over 35 seconds and the encode-worker wait remains active. Camera frames show changing physical output. Six isolated BLE-controlled cases were repeated on this exact image: black, R, G, B, native warm white and mixed RGB. The camera confirms the colour channels and warm/cool white distinction; these short static observations do not establish all-animation or long-run freedom from unintended flashes. Scene, brightness, white mixing and automatic brightness were restored afterward.

Three tablet-mediated Wi-Fi-off/on cycles passed on this image, including encrypted commands offline, continuous uptime, delayed disconnect and subsequent reconnection. A separate test saved Wi-Fi disabled, received the reboot acknowledgement, reconnected the already bonded tablet after the software restart and executed encrypted commands with `wifiEnabled:false` and no LAN. BLE then restored Wi-Fi; LAN returned at 28 seconds uptime, boot reason SW, no retained panic. UART records successful connection and encryption events. These tests establish the current single-controller BLE/offline path; they do not isolate why the earlier recovered image's connection attempts failed.

## Boundaries

The native `nebulite-s3` variant compiles and includes source-verified Croptop/Jacket profiles and authentic assets. No wearable was flashed or physically accepted. MINI80 has a source-verified S3 N8/52-pixel profile; rail sequencing, battery protection and pixel order still need implementation/qualification on its actual board. No generic old `helio1` WLED profile substitutes for it.

No BLE firmware upload is advertised: the app uses the existing HTTP application-image OTA route. Multi-device clock skew, power-cycle bonds on all product boards, interrupted OTA/recovery, and the new PCB lanes are not validated by host tests, a finite timing model, CAD or this sphere.
